# Amethyst signing and trust-cache audit

## Pinned source

The source inspected is Amethyst commit [61ce86d7d3f00e5395f4d42bebda0e5dce04946a](https://github.com/staturnzz/amethyst/commit/61ce86d7d3f00e5395f4d42bebda0e5dce04946a), branch main, tag v1.1. The launch call sites are [launchd_hook/loader.c](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/loader.c#L42-L68) and [base_hook/loader.c](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/base_hook/src/loader.c#L109-L141). Both inspect executable Mach-O slices and only call signing/trust routines when macho_get_signature returns a structure.

## Code-signing path

1. macho_load opens a path read-only, maps it, and accepts ARM64 slices the parser recognizes. macho_get_signature scans the load commands for LC_CODE_SIGNATURE, reads the referenced SuperBlob, selects a CodeDirectory, and computes a CodeDirectory hash. It does not verify every code page against its stored hash or cryptographically validate a CMS signature. Its malformed-input bounds checks are incomplete. [Mach-O load and slice parsing](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_macho.c#L29-L138), [signature extraction](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_macho.c#L195-L265).
2. macho_should_sign chooses regeneration when the CodeDirectory version is at most 0x20001 or the hash type is SHA-1. For a path containing /var/containers it regenerates non-ad-hoc signatures and leaves ad-hoc signatures for trust-cache handling. For other paths it returns false. [macho_should_sign](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_macho.c#L411-L419).
3. When regeneration is selected, launchd_hook calls sign_binary. It opens the path O_RDONLY, builds a new signature blob, submits it through fcntl(F_ADDSIGS), finds the resulting kernel cs_blob, updates its code-signing flags, and flushes data. No pwrite, write, rename, or Mach-O load-command rewrite appears in this path. [sign_binary/create_cs_blob](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/codesign.c#L8-L130).
4. macho_sign_binary hashes code pages into a new CodeDirectory and builds a SuperBlob with the CodeDirectory and, only when it can extract them from an old signature, entitlements. It does not create a CMS signature slot. The CodeDirectory is zero-initialized and the builder does not set its flags field, including the CS_ADHOC bit. If macho_get_signature returns NULL, it sets codeLimit to the whole slice size and can still build a CodeDirectory with no entitlements. [CodeDirectory construction](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_macho.c#L301-L409).

Source therefore confirms an in-memory signature preparation operation passed to the kernel through F_ADDSIGS, not an on-disk signer. The generated CodeDirectory has no CMS signature slot and leaves its flags field zero, while the kernel cs_blob flags are later changed to include CS_VALID and CS_SIGNED. This is not evidence of a conventional on-disk ad-hoc signature. The source does not prove how the iOS 12.5.7 kernel handles a missing LC_CODE_SIGNATURE command. On an ARM64 build, sign_binary also returns success early when the vnode already has a cs_blob; it does not verify that the existing blob matches the requested binary, and that early return does not close the opened file descriptor. On a generated blob, Amethyst clears several enforcement flags and sets CS_VALID, CS_SIGNED, CS_GET_TASK_ALLOW, CS_DEBUGGED, CS_PLATFORM_PATH, CS_PLATFORM_BINARY, and CS_EXECSEG_SKIP_LV. That code-signing state is distinct from the sandbox label. These are broad privileges on the target's code-signing object and must not be applied to unrelated executables.

The generated signature contains no new arbitrary entitlement data. When an existing signature can be parsed, Amethyst may preserve its entitlements while regenerating the CodeDirectory. An unsigned file has no source entitlement blob for this routine to copy. Signing acceptance must not be treated as sandbox exemption, entitlement installation, dynamic-link success, or process startup.

## Signature-state distinctions

| Input state | What the parser/source does | What is established |
| --- | --- | --- |
| Valid signed signature | If a parseable CodeDirectory exists, Amethyst computes its cdhash. Depending on CodeDirectory version, hash type, and path, it may call sign_binary or add that hash to the dynamic trust cache. | The source does not cryptographically verify a CMS signature or page hashes before making this choice. Actual kernel acceptance is not established by source. |
| Ad-hoc signature | macho_get_signature considers the signature ad hoc only when there is no substantive CSSLOT_SIGNATURESLOT blob and the CodeDirectory has the ad-hoc flag. On a modern signature outside /var/containers, macho_should_sign returns false and the cdhash is added to trust-cache. | Ad-hoc is not the same as unsigned: this path needs an existing LC_CODE_SIGNATURE and a parseable CodeDirectory. |
| Invalid signature | If it is malformed enough that no CodeDirectory is returned, both normal callers skip signing and trust-cache insertion. If the CodeDirectory is structurally parseable, the source hashes that CodeDirectory but does not prove its code-page hashes match the file or its CMS is valid. | “Invalid” has multiple parser/runtime meanings. Trusting a cdhash does not repair changed code pages. Runtime acceptance remains unknown. |
| Empty or unusable signature structure | A present LC_CODE_SIGNATURE is not enough: macho_get_signature can return NULL if it cannot find a recognized CodeDirectory. The normal callers then skip preparation. The parser does not provide a dedicated empty-signature repair path. | No source-confirmed repair occurs. Malformed structures may also exercise incomplete bounds checks. |
| No LC_CODE_SIGNATURE | macho_get_signature returns NULL after scanning the load commands. Both process_binary and jbserver_process_binary only sign or trust inside the non-NULL signature branch. | The normal Amethyst launch flow performs no signing or trust-cache action for case D. A lower-level signing routine can build a blob if explicitly invoked, but no current launch caller does so. |

## Jailbreak-server request and privilege path

The base-hook client creates XPC dictionaries with the name com.staturnz.jbserver and numeric command values. It gets a bootstrap pipe from a task bootstrap port and synchronously calls xpc_pipe_routine; it reports client failure when it cannot create that pipe and unknown failure when no reply arrives. [Client transport and request wrappers](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_jbserver.c#L5-L109).

The launchd hook is the server in the target process: on iOS 12 and earlier it hooks the private _xpc_serializer_unpack entry point, and it also hooks _xpc_pipe_handle_mig. It handles the private dictionary name in launchd's XPC receive path. It does not register a documented public XPC service. [XPC dispatch and initialization](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/jbserver.c#L329-L389), [hook registration](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/jbserver.c#L456-L483).

The XPC request types include TRUSTCACHE, SIGN_BINARY, INIT_PROCESS, PLATFORMIZE, UNSANDBOX, SET_UID_GID, and HEARTBEAT. SIGN_BINARY passes a path plus load-command offset/size, slice offset, and file type to sign_binary. In the current server implementation, sign_binary ignores the load-command offset, size, and file-type arguments after receiving them; the client wrapper rejects a zero signature size. This mismatch is an undocumented internal protocol detail, not a stable ABI. [Enums and client signature request](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/include/basebin_jbserver.h#L6-L73), [server request handling](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/jbserver.c#L133-L181).

The server derives the caller identity from the XPC audit token when no target PID is supplied. The inspected request handlers do not show an authorization check before applying an explicit PID, changing sandbox state, or inserting a cdhash. Actual reachability is not established from source alone, but this is not a safe public API. Any project-owned IPC must be root-restricted, authenticate peers, constrain target paths/PIDs, and never expose the Amethyst server requests directly to untrusted clients.

## Trust-cache behavior

trustcache_init reads trust-cache locations and other kernel state from Amethyst's handoff plist. For iOS 12 it selects the dynamic trust-cache V0 representation and, when available, the static SegExtraData representation. It may allocate a wired dynamic trust cache and link it into the kernel's dynamic trust-cache pointer. The initialization code is version-specific and relies on the jailbreak's kernel read/write capability. [Version selection and init](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/trustcache.c#L14-L47), [dynamic cache allocation/linking](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/trustcache.c#L138-L263).

trustcache_add_hash writes a 20-byte cdhash and hash type into the dynamic kernel cache. If no free marker slot remains, trustcache_reset clears the dynamic entries, re-adds selected Amethyst binaries, then restores recent hashes. trustcache_add_binary loads the Mach-O and adds hashes from existing signature structures; it does not create a signature, and it does not resolve or add dependent libraries. [Add/reset/check operations](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/trustcache.c#L274-L425). The launchd-hook trust-cache source has no per-hash removal function, and its header and server protocol expose no removal operation ([header](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/include/trustcache.h#L92-L103)).

These entries are kernel-resident during the current kernel lifetime, not a persistent project database. Source does not show a disk journal for project hashes. A full device reboot discards the in-memory dynamic cache; Amethyst must initialize/repopulate its cache during the next jailbreak session. A userspace or jailbreak-component restart is a separate lifecycle event and must not be assumed to clear or preserve state without device testing. Trust-cache insertion alone does not create a signature, add LC_CODE_SIGNATURE, add entitlements, or change the sandbox label.

## Errors, synchronization, and operational reliability

- macho_load returns NULL for open, parse, allocation, or unsupported-slice failures. The normal preparation callers treat NULL signature as a no-op in an otherwise successfully parsed Mach-O.
- jbserver_process_binary returns an Amethyst error if parsing or an RPC operation fails, but base_hook's spawn handler ignores that result. launchd_hook's process_binary result is also ignored by its spawn handler.
- The server's trust-cache handlers ignore the return from trustcache_lock_add_hash and return JBSERVER_ERR_SUCCESS. trustcache_add_binary also ignores errors from individual trustcache_add_hash calls. In create_cs_blob, Amethyst attempts to add the newly generated cdhash to trust-cache before F_ADDSIGS; the trust-cache add result is ignored, and a later F_ADDSIGS failure can leave a trust entry for a signature that was not attached to the vnode. JBSERVER_ERR_TRUSTCACHE_FAILURE is declared but not used by these paths.
- sign_binary and create_cs_blob return 0/-1. The XPC server maps failure to JBSERVER_ERR_UNKNOWN_FAILURE. The client maps a missing response to JBSERVER_ERR_UNKNOWN_FAILURE. These error values are coarse and do not identify the failing stage.
- Trust-cache lock wrappers use a static pthread mutex around selected read/add helpers. The raw helpers remain callable internally without that lock. There is no corresponding signing mutex or per-file lock around F_ADDSIGS. The XPC bootstrap-pipe cache also has no explicit project-level lock in the inspected client.
- Kernel read/write helpers are void and stop on an underlying Mach error without propagating a result. Some higher-level operations perform readback checks, but the server can still report success after helper paths that do not verify each mutation.

These behaviors do not satisfy iOS-Unsandboxed's non-negotiable “no silent signing failures” requirement. P003 adds only a compatibility result and a pure eligibility policy; it does not call these operations. Any future launch/signing adapter must add a fail-closed result that reports the failed stage and must not launch a target after failed preparation. Concurrent launches of the same path need an inode-pinned transaction or serialization policy before any file or vnode state is changed.

## Source-backed conclusion

For signature-present binaries, Amethyst has source-confirmed pre-launch paths that either add an existing cdhash to its trust cache or create a kernel-attached signature blob and adjust the resulting code-signing flags. These actions depend on Amethyst's private launchd hook, kernel capability, XPC protocol, and initialization state. They are not stable external APIs, and the current caller policy is neither opt-in nor failure-closed.

For a binary with no LC_CODE_SIGNATURE, normal launch preparation is a no-op. The in-memory builder can operate without an old signature if a new caller explicitly invokes it, and sign_binary submits that new blob through F_ADDSIGS without an on-disk write in the inspected userspace code. Whether that is accepted for an unsigned iOS 12.5.7 ARM64 Mach-O, and whether dyld can then complete startup, requires physical-device validation. P002 does not add a new signing mechanism or perform a signing operation.
