## Filters, contexts, and SSH decision

Both hooks skip work when /usr/lib/base_hook.dylib is missing, when the path is empty, for selected exact path-list entries, and for driver process type. The launchd hook additionally gates on initialization/userspace-reboot state, skips /Developer/usr/bin/debugserver, and filters selected Apple XPC bundles. A child is forwarded through the original API when blocked. The path resolver canonicalizes with realpath; its fallback PATH search checks S_ISREG, while the direct realpath case does not perform that check. Neither path checks file ownership/mode or passes an inode-pinned descriptor to the later spawn; a path can change between inspection and use. See [launchd filters](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/src/loader.c#L13-L39), [base-hook filters](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/base_hook/src/loader.c#L19-L31), and [path resolution](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/common/src/basebin_util.c#L180-L222).

The direct SSH workflow therefore depends on two separate events: launchd must get the SSH daemon onto Amethyst's injected path, and the shell that later executes ./binary must have the base hook loaded. The needed extension point for the second event is the base hook's execve_hook/spawn_handler, not a standalone iOS-Unsandboxed daemon. The launch-time signature/trust operation must complete before the original executable launch; Amethyst's current per-process sandbox work occurs later, in the target process's base-hook constructor, before the process reaches its normal program entry. Those operations have separate failure and policy requirements.

## Classification

- **Source-confirmed:** launchd posix_spawn interception; base-hook execve and posix_spawn interception in injected processes; signature/trust preparation calls for parseable signatures; path and process-type filters described above.
- **Technically possible but unverified:** the target SSH daemon and shell receive and retain Amethyst's base hook; a forked SSH session continues to use its patched execve; the reference device accepts its exact launch behavior.
- **Not intercepted by these source call sites:** arbitrary launches from processes without the base hook; fork itself; the launchd hook's execve; the declared but unhooked posix_spawnp; launches bypassing these hooked APIs.
- **Physical-device investigation required:** SSH-launched executable interception, hook initialization on iOS 12.5.7, launch failure modes, and SSH stability.

The project must not add global interception of unrelated Apple executables. The P003 extension needs a default-disabled, narrow eligibility policy in the existing hook path and must leave the original launch untouched on an explicit policy skip. The current Amethyst code is not itself opted-in to iOS-Unsandboxed and does not implement that policy.
