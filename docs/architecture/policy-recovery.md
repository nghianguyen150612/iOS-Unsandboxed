# Policy recovery and lifecycle

Ordinary installation creates no policy and enrolls no scopes. Upgrade and rollback preserve a valid policy byte-for-byte and refuse corrupt, unsafe, unsupported, or unreadable policy instead of migrating it. A rollback to an older helper does not interpret or activate the policy: P010 has no persistent policy reader and remains disabled. Keep the policy for a subsequent supported manager. Package recovery preserves the independent policy and continues to expose diagnostics even when policy is invalid.

Uninstall reports and preserves the policy, valid or foreign, as well as unknown files and `.policy-tmp-*` entries. This can leave the private project directory in place after uninstall. Inspect and archive such data through a trusted root administrator before manual removal; never assume ownership alone establishes provenance. Policy reset only replaces a missing or valid policy with a valid empty preview-only record. It refuses corrupt, unsafe and unsupported files, including foreign collisions. Recovery from those states requires explicit out-of-band administrator investigation; there is no automatic deletion or downgrade. `reset` does not remove installation or stop a service. `remove-directory` removes only the exact metadata entry and never deletes directory contents.

The same advisory lock serializes policy and P007/P008 operations. A crash before rename can leave an orphan temporary file and the previous complete policy; a crash after rename leaves the new complete policy. The lock file persists while the kernel releases its lock on process exit. The tests simulate interrupted writes and concurrent lock contention, but device filesystem crash durability remains NOT RUN.
