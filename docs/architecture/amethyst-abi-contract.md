# Amethyst ABI and integration contract

## Compatibility statement

Amethyst does not expose a stable external C ABI for its launch, signing, trust-cache, or sandbox operations. The inspected binaries compile with hidden visibility and strip symbol information. The source functions discussed here are implementation details inside the Amethyst hook targets. The public-looking headers are build inputs for those targets, not a supported SDK. Source revision: [Amethyst 61ce86d7d3f00e5395f4d42bebda0e5dce04946a](https://github.com/staturnzz/amethyst/commit/61ce86d7d3f00e5395f4d42bebda0e5dce04946a), branch main, tag v1.1.

Every direct native integration described below is version-coupled. The launchd hook uses private kernel layout offsets and private XPC symbols; the base hook's XPC client assumes internal xpc_global_data layout; request enums and fields have no protocol version negotiation. Do not link against or dlsym these internals as if they were stable APIs.

P003 adds a separate project-owned C17 preflight result and pure eligibility policy under `native/include/`. Those interfaces expose no Amethyst structs and do not call the private operations described here. They do not verify the installed Amethyst build, modify an Amethyst hook, or provide launch integration. See [the preflight contract](preflight-contract.md) and [the execution policy](execution-policy.md).

P009 now adds the separate read-only project-owned adapter and capability ABI described in [the adapter contract](amethyst-adapter.md). That ABI only collects bounded evidence and classifies it; none of the mutating execution operations below are implemented.

The server also implements platformize, set_uid_gid, and heartbeat commands. These remain Amethyst-private operations and are not part of the product adapter proposal. In particular, P003 must not use platformize or set_uid_gid as a substitute for the narrow sandbox policy.

The build applies -fvisibility=hidden to both hook dylibs and strips them with strip -x. A source-level non-static function is therefore not evidence of a callable exported symbol. P002 inspected source declarations/call sites, not a device's installed symbol table. See [base_hook/Makefile](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/base_hook/Makefile#L6-L15) and [launchd_hook/Makefile](https://github.com/staturnzz/amethyst/blob/61ce86d7d3f00e5395f4d42bebda0e5dce04946a/basebins/launchd_hook/Makefile#L6-L19).

## Future mutating integration proposal (not implemented in P009)

Rust remains responsible for user-facing CLI commands. A future Rust CLI will send authenticated requests to the project daemon through a project-owned IPC contract. The C17 daemon will own native requests and convert Amethyst-specific failures into stable product errors. The only launch observer is an explicitly reviewed extension to Amethyst's existing base-hook path; a project daemon alone cannot observe every launch.

The narrow product ABI should have four daemon-side operations. A separately reviewed Amethyst base-hook extension must serialize a request to the C17 daemon over a synchronous request/reply channel and wait before continuing. The project daemon does not observe the launch on its own. The Rust CLI uses the daemon only for management commands and policy state.

| Proposed product operation | C-level shape | Contract |
| --- | --- | --- |
| Adapter initialization/status | int iu_amethyst_adapter_init(const struct iu_adapter_config_v1 *, struct iu_result_v1 *); | Called only after daemon startup. Verifies that the expected Amethyst hook/server is live and matches the pinned compatibility profile. A heartbeat alone is insufficient because it does not identify the Amethyst revision. Failure returns a named stage and fails closed. |
| Pre-launch preparation | int iu_amethyst_prepare_exec_v1(const struct iu_exec_request_v1 *, struct iu_result_v1 *); | Invoked by the daemon after it receives a synchronous request from the intercepted process, before the original exec/spawn continues. Request contains ABI version/size, canonical path, device/inode identity, and caller identity. The daemon computes opt-in from root-owned policy; it never trusts an opt-in boolean supplied by the caller. It may request signature/trust work only after policy and pinned compatibility checks pass. |
| Per-process policy | int iu_amethyst_apply_process_v1(const struct iu_process_request_v1 *, struct iu_result_v1 *); | Invoked by the daemon after an opted-in target's constructor sends a synchronous request, before normal program entry. The request names the current process identity; the daemon independently verifies PID, executable path, and file identity against prepared state and policy. It must never infer opt-in from root identity or a broad path prefix. This remains separate from signing/trust work. |
| Adapter shutdown | void iu_amethyst_adapter_shutdown(void); | Stops accepting new adapter work and releases local XPC objects, queues, and locks. It cannot remove a kernel trust entry or vnode cs_blob already created by Amethyst. |

The versioned C layouts should use fixed-width fields and contain no platform-owned pointers on the wire. For example, iu_exec_request_v1 carries uint32_t struct_size and abi_version, uint32_t path_length, int32_t caller_pid, uint32_t caller_uid and caller_gid, uint64_t device, inode, file_size, and a 32-byte SHA-256 digest, followed by path bytes. iu_process_request_v1 carries the same version fields, int32_t target_pid, uint64_t device/inode, and a digest that the daemon checks against the process image and prepared record. The in-process C adapter may use a borrowed const char * path for one synchronous call, but must copy it before queuing work. The serialized request contains the path bytes and fixed-width identity values, not a raw pointer or caller-supplied privilege/opt-in flag.

iu_result_v1 is caller-owned and contains uint32_t struct_size, abi_version, status, and failed_stage, plus int32_t system_errno and amethyst_error. It owns no pointers. Product status must distinguish policy skip, unsupported Mach-O, Amethyst unavailable/version mismatch, signature preparation failure, trust-cache failure, sandbox operation failure, timeout, and internal error. No silent-success conversion is allowed. If an opted-in process cannot apply its required policy before normal program entry, the hook must prevent that process from continuing and report the failure; an unrelated process must continue on its original path.

The future mutating adapter would initialize once per daemon lifecycle, verify dependencies before enable succeeds, and stop accepting work on disable/shutdown. The Amethyst server has no shutdown or kernel-state rollback API, so adapter shutdown could only stop new requests; it cannot claim to remove an already-added trust entry or vnode cs_blob. Calls that prepare an executable require the Amethyst service and kernel state to be initialized. Calls to unsandbox must occur after the target PID exists and before its normal program entry; the existing base-hook constructor is the source-confirmed insertion point for the current process. The launch hook must wait only for a bounded interval and fail closed for the opted-in target if daemon IPC or Amethyst RPC is unavailable.

This is a future project-owned execution contract proposal, not an Amethyst API. P003 implements the independent preflight/eligibility rules; P009 implements only the read-only adapter. Neither modifies a hook or provides an execution operation. Future launch work requires a separately reviewed Amethyst-owned hook modification or compatibility shim to invoke the pre-launch operation from base_hook's execve_hook/spawn_handler. A new dylib placed under `/usr/local/lib/ios-unsandboxed` is not loaded by Amethyst automatically. If a shim communicates with the project daemon over future authenticated IPC, the launch-request verb must be available only to configured caller UIDs through strict peer checks and allowlisted paths; management verbs such as enable/disable remain root-only. The daemon must validate the PID/path/inode itself, reject arbitrary target PIDs, and never expose raw Amethyst operations. P009 pins the source audit, but installed build and runtime mismatch handling still require independent evidence.

## Concurrency and lifecycle assumptions

Trust-cache mutation is synchronized only through specific trustcache_lock_* wrappers. F_ADDSIGS work has no corresponding lock or same-file transaction. The private XPC client has no explicit project-level concurrency guarantee. The product adapter must serialize preparation by stable file identity, avoid path-only authorization, and detect file changes between inspection and launch. Any queue must not delay the exec path indefinitely; timeout and cancellation must return an explicit error and must not continue a targeted launch as if preparation succeeded.

No stable API currently reports a complete initialization version, capability set, or shutdown state. The Amethyst heartbeat returns a sentinel success value but no source revision. A future compatibility shim must introduce a version/capability handshake or verify exact installed component hashes before enabling. Amethyst component restart, userspace reboot, and system reboot invalidate the adapter's assumptions and require re-handshake; all are device-only behavior to validate.
