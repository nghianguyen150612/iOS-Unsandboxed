# Provenance trust model

A SHA-256 digest identifies content relative to a reference; it does not authenticate that reference or establish where the bytes came from. Directory enrollment, ownership, restrictive mode, architecture, CodeDirectory parsing, and an administrator's label express local facts or intent. None authenticates a publisher or demonstrates that an executable is not a copied Apple system binary. A valid publisher signature alone would also not establish an adequate non-protected origin policy.

P013's Rust verifier uses Ed25519 via `ed25519-dalek` and a canonical signed manifest. P013C's `iu provenance plan MANIFEST ARTIFACT` composes that verifier with the production root-owned publisher store and P012's borrowed-descriptor preview. It accepts no caller-supplied verification booleans and does not use the legacy C v1 provenance result as cryptographic proof. Test-only trust fixtures enter through private test closures and isolated temporary roots; production has no environment variable or runtime selector for them. Unknown, revoked, pending, inconsistent, or stale trust state fails closed.

The local store and generation marker support key lifecycle and detect local inconsistencies while the marker remains present, but they are not an independent monotonic anchor; `ROLLBACK_PROTECTION_UNVERIFIED` remains explicit. Publisher authentication only confirms that the active publisher key signed a statement matching the exact opened artifact. Build origin remains `ORIGIN_UNVERIFIED`, protected origin remains `UNKNOWN`, and P003 remains disabled. A distinct independent provenance provider and reviewed protected-artifact classification with defensible completeness assumptions are still required. Do not infer non-Apple origin from failure to match a small database. Even authenticated evidence never authorizes launch.
